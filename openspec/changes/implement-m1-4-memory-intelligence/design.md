## Memory foundation

Pure core types validate required YAML fields and kebab-case names, one-line descriptions, known memory types and nonempty content. Feedback/project notes require nonempty Why and How to apply lines. Parse diagnostics do not echo supplied text. Write validation scans the entire input, including frontmatter, for credential patterns, private keys and high-entropy strings longer than 32 characters. Parsing an existing document remains distinct from admitting a write.

Index rendering sorts unique validated names, uses local Markdown filenames and escapes link labels/descriptions. Duplicate names are refused at this layer; storage will replace matching names before rendering. Index loading keeps the first 200 lines or 25,000 UTF-8 bytes, whichever is smaller, and adds the canonical truncation notice. Typed settings default enabled/generate to true; the existing EnvSource flag semantics implement CYBER_DISABLE_MEMORY. Project IDs are validated as safe components before deriving data/memory paths.

The document increment has no runtime entry point. The read-side storage increment uses cap-std directory handles and cap-fs-ext no-follow directory/file opens, private Unix creation and descriptor-based permissions, bounded note/catalog reads and independent OS file-lock scope claims. Existing review creates no directories; claiming a scope explicitly creates its lock file. Index reads consume at most 25,004 bytes to determine the canonical 25,000-byte/200-line UTF-8 prefix without reading note bodies. Any pending .memory-transaction entry fences reads and retains evidence; no transaction is automatically adopted as a live owner. Read-side limits are 1 MiB per note, 4 MiB of catalog metadata and 4096 directory entries, with explicit refusal rather than partial success. Windows file/directory ACL privacy and full native acceptance remain open. Journal creation and explicit Unix note/index mutation recovery now use the protocol below. Automatic reconciliation, reviewed conflict resolution, Windows mutation support and runtime integration remain required. Tools, HTTP, CLI/TUI and Context Source reconciliation must use the same validation and storage owner. Read-only generation and disabled memory must be enforced at dispatch, not only in model instructions.

## Journaled Unix mutation protocol

A mutable scope guard admits a prepared mutation only after bounded write validation, filtered catalog construction and before-state fingerprints. A private .memory-transaction directory holds synced desired note/index files and an immutable versioned intent. Pending preparations fence ordinary reads. Commit first archives the original target within the transaction, verifies its fingerprint, then installs staged data with a create-only hard link; recovery normalizes only an exact same-inode/hash two-link staging pair. It verifies other valid note fingerprints, target/index after states and archived before states before acknowledging completion. Conflicting files are preserved and keep the scope fenced. Completed transactions move into private .memory-history/<id>/ so archived original inodes remain named even for a late editor write. Directory/file syncing and all namespace operations retain directory-bound authority. Unknown preparations or incomplete manifests are not replayed. Windows mutation admission remains refused until ACL privacy and durability are integrated; full platform acceptance remains required.

On Linux, capability directory handles use O_PATH and cannot perform fchmod or fsync. Permission changes and durability barriers therefore open a readable dot-directory handle relative to the retained capability, with no-follow semantics and directory verification. The regression retains the original directory after namespace replacement and verifies permissions and syncing affect that inode. A native Linux result is required in addition to local macOS evidence.

## Built-in memory tool integration

The built-in memory tool accepts only project/global scopes and list/read/write/update/delete operations. Disabled memory removes the definition and refuses direct dispatch; read-only settings and Plan Mode project a list/read schema and refuse mutations again at execution. Scope permission defaults allow only the two managed scope selectors, with configured, agent, Session, inherited and hook decisions retaining precedence. Authorization precedes project identification and storage effects. The tool uses the existing host data-directory convention (parent of its managed tool-output directory), validates writes before opening storage and never automatically recovers a pending journal. Blocking filesystem work is joined through completion, so cancelling an async caller cannot dispose a started mutation owner; cancellation is checked before admission. A completed mutation returns its receipt rather than a false aborted result. Crash outcomes remain unknown without automatic tool replay. Context reconciliation and client/event delivery remain separate required integrations.

## Owned memory Context Source observation

Disabled or unavailable built-in memory definitions withdraw core/memory without storage admission. CLI/TUI/API/events, unknown-effect review and complete platform acceptance remain required.

Outside Git, project identity resolves to global. Context loading admits only an allowed canonical scope, with denied/ask scopes withheld. The regression fails against the committed f918310 tool implementation and passes after correction.

## CLI memory review and editing

The authorized CLI surface adds memory list/show/path/edit/delete and debug memory, without opening a database or starting model work. Review reads use existing bounded directory authority. Mutations honor current memory settings and platform privacy/durability admission. The editor works on a retained private draft outside the memory directories, with no-follow regular-file reads and hard-link rejection, rather than changing memory before write validation. ## HTTP memory mutations and shutdown ownership

PUT /memory/{scope}/{name} accepts a strict JSON content object containing the complete Markdown document; DELETE accepts no body. The application validates before storage admission and repeats current enabled/generate settings under scope ownership. A retained blocking worker owns the shared journal and an owned runtime lifecycle read lease, so disconnect or future disposal does not release shutdown ownership of admitted work. Completed requests replay their receipt without repeating files or events. The standard response cache remains in place; memory admission additionally pins the full method/URI/Location/body digest to protect global idempotency identity across response-cache gaps and endpoint reuse. Unknown memory admissions remain fenced and are not cached as terminal failures. Contention before admission returns retryable 503 without caching. Reviewed reconciliation of unknown database/file effects remains required.

### Explicit storage recovery review
Expose read-only inspection and fingerprint-bound recovery in the shared core. Bind the scope and journal directory identities, intent, all known transaction artifacts, current note/index and catalog fingerprints. Validate desired content and preflight slots without normalizing links. Unsafe partial link states remain refused by this review interface pending dedicated alias review. Recapture before effects; acknowledgement uses the existing durable commit boundary. This does not reconcile database admission owners or enable automatic recovery.

### Local CLI recovery controls
`memory recovery` prints read-only review, including proposed note content and the fingerprint, with null for absent evidence. `memory recover --review` validates a SHA-256 fingerprint and repeats settings under the scope claim. Before file effects it checks an existing database through read-only SQLite for pending scope admissions, refusing unresolved ownership or unverifiable inspection; no database is created. In-memory databases cannot prove ownership absence and refuse. This prevents file-only recovery from releasing a journal fence belonging to a durable unknown request. Database reconciliation remains a separate required control.

### Admission-to-journal binding
Before installation, persist an owner-authorized memory.mutation.journal_bound.1 event containing the exact core transaction receipt and a SHA-256 digest of the complete validated intent (before/after note/index hashes and catalog). Completion of new writes requires that bound receipt at the next sequence. Historical completion projection retains its original unbound sequence for event replay only; new live owners cannot complete unbound writes. This is evidence for later fresh reviewed reconciliation, not recovery authority; legacy pending admissions remain unproven.

Journal binding rotates the admission nonce atomically in its projector. The binding event reveals only the superseded nonce and the new nonce hash; the new live key remains solely with the retained owner. Thus stored binding evidence cannot authorize completion after owner loss.

### Fresh reviewed reconciliation in the runtime
Join admission and aggregate sequence into one database review, binding request/result/sequence and the exact physical journal identity. Require a fresh current-state storage review under the retained scope claim before durable takeover. A reviewed recovery event compares database fingerprint and original owner hash atomically, records the matching journal and a newly minted owner hash, and advances the recovery sequence. No persisted nonce is reused. Completion projects against that sequence and exact receipt. Already acknowledged matching journals return their original change and finish archival without another event. Unbound historical pending requests remain refused until a separate explicit legacy resolution contract is implemented. HTTP/CLI/TUI authorization and lifecycle gates must surround this runtime interface when exposed to users.

### Authenticated recovery controls

GET returns null for absent journal and a paired storage/admission review for pinned durable journals, retaining manual review when generation is disabled. No raw execution capabilities are exposed. Generic HTTP idempotency caches successful replay; after response-cache loss the consumed review refuses rather than repeating effects. ### Durable recovery request identities
Project an optional hashed HTTP request key and full request digest from the reviewed takeover event into memory_recovery_request, keyed uniquely and linked to the original memory mutation. Both ordinary memory admission and recovery takeover reject cross-ledger key reuse atomically. Receipt/status lookup joins the original admission/result without executing journal intent. Unresolved attempts remain fenced; an explicit later review may resolve the same pinned mutation, after which retained attempt keys report its receipt. POST replay resolves completed durable identity before storage/settings effects; GET lookup checks canonical Location/project. Unkeyed requests retain stale-review refusal without promising key lookup.

CLI database/file reconciliation uses explicit `--server` admission through an already registered TCP server. Paired fingerprints and a user-retained request key are mandatory for confirmation; the client issues one request and exposes separate receipt lookup after uncertain transport. It never opens the database directly or starts a model/server. Default local file review and pending-admission refusal remain available.

### TUI review and confirmation
The /memory overlay owns generation-bound project/global catalogs, selected note content, paired recovery review and an explicit confirmation step. Scope, Session and Location changes invalidate review and stale responses; failed requests clear actionable content. Deletion requires first opening the note and confirming Y. Recovery displays proposed content, paired fingerprints and completion status before C/Y confirmation. ### Windows memory handle verification foundation

The Windows backend queries only retained handles. It preserves the full volume/128-bit file identity, rejects reparse-point handles and multiple links for regular files, and validates a protected non-null DACL owned by the process user. Only that user and SYSTEM may receive allowed ACEs; denied ACEs grant no access, while unsupported ACE forms refuse. Token buffers and SID slices are bounded and native allocations/token handles have scoped owners. Existing permissions are never repaired by this verifier. The metadata guard is integrated into memory regular-file reads and scope directory identity checks; private ACL verification is a separate primitive until atomic private creation and native durable updates are ready. Mutation and client-checkpoint platform gates remain unchanged.

This follows Microsoft's handle-oriented [GetSecurityInfo contract](https://learn.microsoft.com/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo) and the full-identity guidance in [BY_HANDLE_FILE_INFORMATION](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/fileapi/ns-fileapi-by_handle_file_information.md). Native execution remains required. A local Windows-target harness includes the actual backend source and its unit tests with only a small error-type adapter; its successful type/lint check proves neither full core integration nor Windows API runtime behavior. CI runs the actual core backend tests and the memory-storage integration test.


### Windows private create-only child primitives

Private child creation now uses NtCreateFile with a retained directory handle as RootDirectory and one bounded ASCII component, OBJ_DONT_REPARSE, case-insensitive create-only disposition, synchronous IO and an explicit protected current-user/SYSTEM-only security descriptor. Regular-file creation additionally verifies a private parent. It refuses collisions without opening/truncating existing children and verifies the returned handle before callers write content. The file API does not reopen the parent path: a moved retained parent receives the child while a replacement path remains untouched. Directory bootstrap leaves caller-selected parent routing/binding to its owner. Traversal, separators, streams, reserved DOS names and trailing-dot/space aliases refuse. No inherited-default window or post-creation ACL repair is used.

The [OBJECT_ATTRIBUTES contract](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes) defines handle-relative lookup, no-reparse resolution and creation-time security. These primitives remain separate from storage startup, journal/checkpoint installation and directory durability. Windows activation still requires those integrations and native execution. The native primitive tests run directly after Windows lint, producing focused runtime evidence before the longer Windows build suite; their outcome remains part of the required dependency result.
