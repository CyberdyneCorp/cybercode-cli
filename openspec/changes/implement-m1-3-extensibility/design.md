## Context

Project executable configuration is currently withheld until checkout trust is approved. Configuration merges and validates before building runtime consumers. Hooks have a canonical target specification but no execution implementation.

## Decisions

- Start with one typed hook configuration model shared by validation and future execution. Validate known events, four P1 handler types, required handler fields, timeout/control types and selector syntax. Configuration validation performs no effects.
- Keep untrusted project/local definitions withheld before interpretation. Checkout trust is not a substitute for the required individual handler-digest approvals.
- Store handler approvals separately from workspace configuration approvals in the same private trust file. Hash canonical effective handler definitions (including defaults and all execution options); invocation approvals retain only inspected digests in memory. Serialize all shared-file mutations with a native sidecar lock, and checkout revocation clears both approval classes. Runtime dispatch must still recheck trust before effects.
- Add ordered scope contributions with per-definition provenance before dispatch; ordinary last-value replacement must not discard earlier hooks.
- Accumulate event arrays inside named profiles as well as top-level hooks. On profile selection, remap indexed hook origins into their new appended positions; ordinary profile settings retain their existing profile labels. Source paths remain necessary for later scope classification and individual handler trust.
- Runtime admission owns prompt hooks; the tool host owns tool hooks and revalidation. Permission denies and protected ceilings remain independent of hook allows. Every execution needs a durable receipt and cancellation owner.
- Construct immutable envelopes from the owning runtime's captured Session/Location/agent/Mode identity and Unix-millisecond timestamp. Event-specific data cannot replace any common envelope field. Chained tool rewrites clone only tool input, preserving identity; core shape validation is not proof of runtime authority or ownership.
- Compile selectors at catalog construction and keep matching side-effect free. Decision parsing reports ignored fields separately for later debug logging. Declared-order merging retains restrictive decisions, rewrite/context accumulation and stop flags; the future dispatcher must feed each rewritten input to the next handler and the tool host must revalidate it before effects.
- Implement process-tree ownership, sandbox selection and bounded IO before command execution. HTTP, evaluator and MCP handlers share the event and decision model while retaining their own authentication and usage boundaries.
- Command transport accepts an already authorized process under the caller's retained execution owner. Feed JSON stdin and drain stdout/stderr concurrently, retaining at most 1 MiB per output stream while draining overflow. Explicit stop attempts terminate the owned tree and wait at most two seconds for acknowledgement; missing acknowledgement remains explicit. The stdin-preserving container adapter is separate from shell tools' EOF adapter. Capture remains transient and is not automatically persisted; runtime receipts must honor hook IO logging policy.
- Command launch resolves the requested handler from loaded provenance again, binds the event Location to the resolved checkout, and rechecks durable checkout and individual approvals before effects. Required hook sandboxing always uses workspace-write enforcement even if ordinary tools have explicit full access. The noninteractive command runner uses the network allowlist without granting unknown domains; interactive network decisions remain a runtime integration requirement. Per-command private scratch is retained after unacknowledged settlement or caller disposal. Windows ordinary full-access launch uses an explicit parent-job event-stdin route: assign the helper before writing the private permit, consume that prefix without buffered read-ahead, then retain the pipe for event bytes and EOF. PowerShell source uses the existing encoded-command argument builder. Required Windows confinement still refuses through sandbox selection until its native hook launch route is integrated.
- Hook receipts use independent execution aggregates so terminal recording cannot race the Session state cache. Admission and its SQL projection commit through the existing single writer with captured Session/ancestor fences. An opaque execution owner records settlement once; owner disposal records explicit unknown/error evidence, and a missing receipt never authorizes replay. IO logging is pinned at admission and raw buffers are omitted unless enabled. Recorded command runs reserve tracked native activity, reverify its authority and persist a launch marker before spawn. Runtime subtree cancellation reaches the process owner and waits for acknowledged native settlement; disposal after the marker preserves unknown activity alongside the hook receipt. Terminal receipts remain admissible after scope closure; dispatch still must verify the owner authority before effects and before applying decisions. Cross-process recovery and full client observability remain separate acceptance requirements.
- Attach a full provenance-preserving configuration resolver to the built-in host at application construction. Built-in command PreToolUse runs before permission evaluation; chained rewrites are revalidated against the tool schema and exact replay approval. Hook allow skips only remaining asks after deny rules and hard Mode ceilings. Command success/failure post events retain the invocation identity and final input. Remaining handler types, optional scheduling/context/continuation fields, remote-tool hooks and all other lifecycle events remain required. Unsupported effectful handler options are reported without launching them until their owner semantics are implemented.
- Deliver the remaining lifecycle events, trust/viewer/test CLI, plugin process protocol/package and MCP OAuth/search as subsequent increments under this same change.

Local connections use a dedicated `mcs_` aggregate and `mcp.status.changed.1` receipts rather than borrowing a Session. Admission is unique for an unsettled canonical Location/server name. ### Retryable MCP startup joins

Shared connection entries retain their startup JoinHandle behind an async mutex. Shutdown awaits the handle by mutable reference and removes it only after terminal completion. Disposing a shutdown future therefore releases the mutex without detaching ownership; a later shutdown joins the same startup before attempting native settlement. Connection cancellation also interrupts queued and active RPC waits independently of the Session token, so shutdown can acquire the native owner and persist actual termination evidence. The public Location-close API is described below; unknown startup effects still require recovery.

### Location-scoped MCP close

The shared host canonicalizes the selected Location and places an admission fence before selecting its entries. It cancels every selected connection, joins retained startup tasks, explicitly shuts down each retained native owner and disposes acknowledged owners only after durable settlement. All selected entries receive a stop attempt even if another fails. Errors or unsettled durable records preserve the admission fence and retained entries for retry/recovery; an absent live object never proves that prior native effects stopped. Successful close removes only the selected entry incarnations and permits a new open with new registration identities. Sibling Locations remain active. The public close API is described below; user interface wiring, cross-process recovery and full native acceptance remain open.

### Public MCP close and scoped replay

The authenticated Location router exposes POST `/mcp/close` without a request body. Idempotency request hashes now include the full request URI and effective canonical Location, with length-prefixed fields for method, URI, directory and body. Query Location overrides the header as in ordinary routing. Invalid routing remains part of identity and is rejected by handlers. A key used at another Location therefore conflicts instead of replaying that Location's success. Existing stored hashes use the previous identity encoding and will conservatively conflict until the 24-hour retention expires; they are not reinterpreted as authority for new effects.

### Retained idle local loss monitoring

Each ready local entry owns a retained monitor task that observes idle connections once per second. It uses try_lock on the native owner, so active RPCs keep exclusive protocol ownership. ### Owned launch retry evidence

LocalLaunchError::retry_safe is a private-construction settlement signal, separate from native acknowledgement. Acknowledged shutdown alone cannot authorize replacing an owner. Prepared-resource failures explicitly stop/join the proxy and retain scratch for caller-owned durable settlement. Unowned launch errors never assert retry safety. Owned discovery failures first commit terminal ownership, settle actual checkout leases while retaining their locks, remove scratch and then mark the error safe. If connected publication fails, the live transport is explicitly stopped and the same complete settlement is required. Native, database, lease or scratch failure leaves the signal false, including acknowledged native shutdown with an Unknown durable record. This is evidence for the upcoming reconnect scheduler, not an implemented retry loop or permission to replay a tool call.


### Retained local MCP reconnect

Entry cancellation represents Location/runtime lifetime, rather than individual connection loss. The retained monitor removes discovery and marks observed loss, explicitly settles the same native owner, verifies scratch removal while checkout locks remain retained, then disposes it before retry. Failed settlement retains the actor and stops automatic replacement. A separate loss marker prevents stale committed Running observations from reporting connected after loss.

The monitor retains the entire retry loop in its original JoinHandle. Each loss sequence schedules at most ten attempts after 1, 2, 4, 8, 16, 32, 60, 60, 60 and 60 seconds. Success returns to monitoring; unsafe failure stops. Every attempt upgrades a weak host only for connection work, resolves fresh full configuration and server authorization, requires the unchanged definition digest, claims actual checkout pins and admits a fresh mcs owner with committed status events. Only complete owned-launch retry evidence permits another attempt after startup failure. Cancelled initialization remains Unknown and fences replacement; close joins the original monitor and refuses unresolved durable ownership. Sleeping backoff retains no strong host reference.

Calls remain single-attempt. Interrupted RPCs withdraw discovery and explicitly stop the original owner; reconnect can restore transport availability but never resubmit arguments. New connection identities make every old registration stale, including calls waiting for hooks/permissions or owner locks. Remote reconnect, manual retry controls, changed-definition reconfiguration and full native platform acceptance remain separate requirements.


### Named MCP startup wait tool

wait_for_mcp accepts a nonempty unique servers array and an optional integer timeout from zero to sixty seconds (default sixty). It uses ordinary built-in schema, agent, hooks and permission boundaries, authorizing a read-only wait_for_mcp action for the requested server names. It polls fresh canonical Location snapshots without starting connections, invoking peers, acquiring RPC owner locks or creating independent ownership events. The result contains redacted statuses and a timed_out flag, with normal output budgeting. Session cancellation stops the wait. Tools are materialized again on following Turns after readiness; waiting cannot mutate a previously advertised Turn catalog or authorize newly discovered executors.


### Scope-aware deferred tool materialization

Registration factories assign explicit builtin, plugin, MCP or Session scope; names and opaque registration strings do not infer scope. This preserves a higher client registration using an MCP-looking name as Session scope. Fresh runtime preflight compares scope as well as registration identity. DeferredToolSettings validates the sole tool_output.deferred_threshold_tokens key, defaulting to 10000; there is no MCP-specific threshold. Nonnegative integer values are accepted, including zero.
