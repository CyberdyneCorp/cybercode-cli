# Windows boundary audit

Source inspected: `4ceb12c`. This is a source audit, not a Windows compilation or enforcement result.

| Boundary | Current behavior | Required M1.1 work |
|---|---|---|
| Sandbox launch | `cyber-sandbox/src/lib.rs` reports enforcement unavailable outside macOS/Linux; explicit full access skips wrapping. | Add an isolated Windows launch interface with restricted token, AppContainer, scoped ACL lifetime and job-object ownership. Preserve failure behavior. |
| Linux helper binary | `cyber-sandbox-exec.rs` imports Unix sockets and Unix exit-status extensions unconditionally. | Gate this Linux-only executable or provide a platform-specific entry point before building the workspace on Windows. |
| Shell selection | Both app defaults and the bash tool fallback use `/bin/sh`; the tool recognizes Unix shells. | Define supported Windows shell invocation and quoting. Test paths containing spaces and metacharacters without widening permission classification. |
| Descendant cancellation | `bash.rs` kills a Unix process group; the non-Unix `kill_group` is empty. | Own all launched descendants in a job object and terminate them on cancellation/timeout, including full-access execution. |
| Service shutdown | `registration.rs::stop_service` invokes the external `kill` command. | Use an authenticated shutdown route or native process signaling with identity checks. Do not substitute unchecked PID termination. |
| Server signals | `server.rs` handles SIGINT/SIGTERM on Unix and Ctrl-C elsewhere. | Verify Windows service lifecycle and ensure orderly registration, lock and database cleanup. |
| Proxy reachability | Existing Windows proxy endpoint would be TCP loopback, while sandbox enforcement is unavailable. | Prove an AppContainer can reach only the intended proxy transport while direct outbound and other loopback connections remain blocked. A general loopback exemption is insufficient evidence. |

Native Windows tests must establish process-tree cleanup, allowed workspace mutations, denied outside reads/writes, credential isolation, proxy-only networking and fail-closed setup errors. Cross-compilation alone cannot establish these properties.

## Profile and direct-object ACL ownership foundation

`windows_container` creates a unique AppContainer profile without capabilities and copies its SID into aligned owned storage. Creation never falls back to an existing identity. Profile clones and direct-object ACL leases retain ownership; explicit deletion refuses while other owners remain. The allocation follows Microsoft's [profile API ownership contract](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createappcontainerprofile).

Each lease retains a file handle opened with reparse-point inspection, rejects a leaf reparse point or null DACL, and adds one non-inheritable read or write grant. Cleanup rereads the current ACL through that same handle and revokes only the invocation SID, preserving unrelated grants added during the lease. Same-identity overlapping leases are refused. Our ACL updates are serialized within the process; arbitrary concurrent external ACL edits are not an atomic compare-and-swap. Merged ACL allocation follows [SetEntriesInAclW](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setentriesinaclw). Explicit cleanup returns errors and drop cleanup logs failures.

Five native tests cover identity uniqueness/deletion, overlapping grants, ACL permissions and preservation, path replacement, drop/setup failure and directory-junction refusal. Cross-target Windows Clippy, all five native tests and the full Windows job pass at `1ec59c3` ([CI evidence](https://github.com/CyberdyneCorp/cybercode-cli/actions/runs/37433709007/job/112170302797)). These primitives are not connected to command launch. Restricted-token launch, recursive root/exclusion policy, ancestor reparse races, credential and network isolation, and kill-9/orphan ACL recovery remain required before availability can become true.

The runtime/tool-host ownership-cycle regression also passes on native Windows at `2bfca16`, together with the full Windows job ([CI evidence](https://github.com/CyberdyneCorp/cybercode-cli/actions/runs/37431885961/job/112164421160)). Active-owner cancellation remains a separate lifecycle gate.

## Suspended AppContainer launch

`windows_launch` prepares a capability-free security attribute list and creates the process suspended, with absolute application/cwd paths, an explicit Unicode environment and no inherited handles. Process-creation attributes assign the child to the parent-owned job atomically. It then verifies job membership and the token's AppContainer flag and exact profile SID, and resumes only after those checks. The job-list attribute requires Windows 10 or newer and prevents an unassigned suspended orphan if the parent dies during creation. An owner guard terminates the primary process on setup failure or drop and closes the descendant-owning job. The launch sequence uses the documented [job-list attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), [AppContainer process attributes](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) and [handle-inheritance boundary](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes).

Windows cross-target Clippy passes. Native tests are queued for direct-file allow/deny behavior, loopback denial, explicit environment and argument delivery, invalid-input refusal and retained-handle termination after owner drop. This path has no redirected shell I/O and does not prepare recursive writable roots or exclusions. It does not enable built-in sandbox availability. Restricted-token policy, root/credential isolation, proxy-only networking, descendants on this launch path and crash recovery still require native proof and integration.

The first native launch run at `f018061` compiled and passed Clippy but both real-worker launches returned Windows error 203 before worker execution ([CI evidence](https://github.com/CyberdyneCorp/cybercode-cli/actions/runs/37436562726/job/112179700065)). ## Explicit AppContainer standard streams

`spawn_with_stdio` accepts three borrowed stream handles, duplicates them with their existing access rights for inheritance and places exactly those duplicates in `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. The duplicate owners and attribute buffers remain live through synchronous process creation and are released on success or failure; original caller handles remain owned by the caller. The no-stream entry point still disables handle inheritance. The implementation follows the Windows [standard-stream inheritance contract](https://learn.microsoft.com/en-us/windows/win32/procthread/inheritance). This API deliberately grants access through these handles; callers must supply streams with only intended read/write access.

The native fixture feeds UTF-8 input through a read-only file handle, verifies EOF, captures separate Unicode stdout/stderr and attempts to signal an unrelated inheritable event. A parent-side positive control verifies that event identity before launch. Windows cross-target Clippy, the 12 local sandbox tests and all 56 strict specification checks pass. Native stream execution remains pending. This foundation still needs pipe/cancellation integration in the actual tool launcher, recursive root policy, network enforcement and crash recovery before sandbox availability can be enabled.
