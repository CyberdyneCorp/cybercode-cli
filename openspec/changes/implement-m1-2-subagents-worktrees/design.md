## Design
Use shared typed settings and a validated worktree-name type so CLI, API and tools cannot disagree on defaults or accept path traversal. Resolve settings only after configuration layering, substitutions and workspace trust; project setup commands remain gated. This first stage does not execute Git or setup commands.

Managed lifecycle operations will serialize per repository using the specified cross-process lock and retain ownership records linking roots, base revisions, branches and sessions. Creation must account for cancellation and cleanup without removing user work. Copy inclusion must honor Git ignore syntax and never overwrite tracked paths. Setup executes through existing sandbox/process ownership. Removal refuses active sessions; auto cleanup checks dirty and ahead state.

Child-session orchestration will use existing durable admission and drain ownership rather than an independent model loop. Permissions are inherited ceilings; a concurrent permit is acquired before creating a child and released on every termination route. Structured output validates the supplied schema and allows exactly one reprompt. Background handback uses the durable parent inbox, and forks take committed parent context through the spawning point. Worktree cleanup and cost attribution remain owned through settlement.

## Verification
Shared configuration/naming tests are groundwork, not proof of worktree isolation. Integration gates require real temporary Git repositories, concurrent processes, dirty/ahead preservation, session ownership, sandboxed setup, and child-runtime tests with deterministic providers. Native platform execution is required for subprocess and file-lock behavior. Keep M1.2 open until all product surfaces and behavioral contracts pass.


### Repository lock ownership
Use the standard-library file lock API, available at the workspace Rust 1.89 minimum, on the persistent `cyber-worktree.lock` file. Open read/write without truncating, try an exclusive lock without blocking and distinguish contention from I/O failure. A non-cloneable guard owns the file handle; drop or process termination releases it. Never unlink the file as cleanup, which could split cooperating processes across different lock-file identities. The lifecycle manager must resolve the shared repository Git directory before acquiring this primitive and hold it through a complete operation. Async contention polling must remain cancellable; active-session refusal is a separate durable ownership check. Native tests must prove independent processes contend, owner disposal releases, forced owner termination releases and separate repositories do not contend. These primitives alone do not close the concurrency requirement.


### Managed Git creation
A shared repository manager resolves root/common Git directories through an injected Git execution port. The application must supply sandboxed, cancellation-owned execution; the core manager has no default subprocess launcher. All mutating creation phases share the repository lock. Resolve the base to a verified commit ID, validate the complete branch name through Git and write a pending ownership record before creation. Never adopt an existing unowned target or branch. Successful creation records ready ownership; error/cancellation leaves pending evidence and preserves paths/branches for recovery rather than retrying checkout over possible user edits. Reuse checks the registered path, common repository directory and branch against ownership before returning, without resetting files. Session ownership, setup/includes, cleanup and recovery settlement remain subsequent required integration.

The cancellation regression observed lock contention immediately after dropping the creation future during parallel Git execution. Normal guard disposal now explicitly unlocks before closing the handle, rather than relying only on last-handle close; transient inherited descriptors must not extend normal ownership. Keep the cancellation assertion immediate and retain the independent-process forced-termination test.


### Git-for-Windows path arguments
Native execution at `2f8f199` proves config and lock ownership, but Git rejects verbatim canonical target paths (`//?/C:/...`). Preserve canonical paths in records and filesystem checks; normalize only explicit Git path arguments into equivalent drive/UNC spelling and enable command-local `core.longpaths=true`. Do not change system/global Git settings. Refuse namespaces or filename components whose meaning changes when the verbatim prefix is removed, before writing ownership or creating a branch. Preserve Unicode through UTF-16 conversion. Native regression covers ordinary canonical targets, long paths and refusal of ambiguous names.

Native worktree execution at `1aeb710` passes seven repository cases but the long target fails in Git's automatic checkout with `$GIT_DIR too big`. Separate registration (`worktree add --no-checkout`) from index loading and checkout executed in the new directory with ambient Git overrides removed. Keep `checkout-index --all` non-forcing: a file created after registration must cause a pending creation error, preserving that file. Pending ownership spans all three stages; failure/cancellation tests retain completed checkout and user-file preservation controls. The existing long-path test remains required.

At `3405edc`, eight of nine native repository cases pass; long-path creation instead fails with Windows process-launch error 267. Windows launches now use a normalized ancestor shorter than 240 UTF-16 units and an explicit Git `-C` argument selecting the canonical requested directory's equivalent spelling. This applies to creation, verification and reuse; Git handles the directory switch after process creation. Runtime sandbox scope must follow the requested worktree rather than grant the launch ancestor. The native execution fixture checks short process directories, retains the long-path creation/reuse assertion and injects checkout collisions into the logical `-C` directory.

At `2e2c73c`, Git starts but rejects the early long `-C` change. Explicit long worktree setup also resolves paths before long-path configuration is initialized. For long linked worktrees, use the verified short metadata directory for index/branch/common-directory operations and an explicit absolute `checkout-index --prefix` destination. Do not enter the long directory during Git setup. Verify the regular `.git` marker and metadata's `gitdir` backpointer canonically in both directions, retaining common-repository, branch and registration checks. Normal short-directory discovery is unchanged. Refuse unsupported long metadata directories rather than redirecting to a different repository or launching through an unverified alias. The original long-target creation/reuse and collision-preservation tests remain required.

### Untracked inclusion

Read `.worktreeinclude` through an opened source-directory capability and compile gitignore patterns with the existing `ignore` crate. Enumerate untracked files with NUL-delimited Git output, including gitignored files such as `.env`, and exclude paths tracked in the destination index. Validate relative paths before access. Copy regular files through confined source/destination directory handles, creating destination files exclusively; reject symlinks, special files and unsafe paths rather than copying outside either root. Preserve file permissions before copying content, record SHA-256 hashes of copied bytes for future cleanup accounting, and keep creation pending on any error. Reuse never repeats copying. Reverify repository ownership after inclusion before marking ready. Sandbox setup and runtime integration remain separate open tasks.

### Setup dispatch

The core setup dispatcher holds the repository lock, checks the supplied ownership against the persisted ready record and verifies repository/branch registration before invoking any setup command. Resolved settings must already have passed workspace trust. A required execution port receives the canonical worktree directory and an unbuffered event sink; there is no default host launcher. The runtime adapter owns sandbox permissions, credential filtering, process-tree settlement and delivery into the Session. Commands run sequentially and stop on the first nonzero or signal exit; lifecycle events bracket streamed byte chunks without requiring UTF-8. Exceptions, event delivery failure and cancellation leave files and ownership intact. Explicit setup invocation is not an automatic retry: durable runtime settlement must prevent blindly repeating side-effectful commands after interruption. Core tests with an injected execution port are foundation evidence, not acceptance of sandbox/process ownership or Session delivery.
