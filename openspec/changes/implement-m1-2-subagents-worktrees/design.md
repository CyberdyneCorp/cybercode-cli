## Design
Use shared typed settings and a validated worktree-name type so CLI, API and tools cannot disagree on defaults or accept path traversal. Resolve settings only after configuration layering, substitutions and workspace trust; project setup commands remain gated. This first stage does not execute Git or setup commands.

Managed lifecycle operations will serialize per repository using the specified cross-process lock and retain ownership records linking roots, base revisions, branches and sessions. Creation must account for cancellation and cleanup without removing user work. Copy inclusion must honor Git ignore syntax and never overwrite tracked paths. Setup executes through existing sandbox/process ownership. Removal refuses active sessions; auto cleanup checks dirty and ahead state.

Child-session orchestration will use existing durable admission and drain ownership rather than an independent model loop. Permissions are inherited ceilings; a concurrent permit is acquired before creating a child and released on every termination route. Structured output validates the supplied schema and allows exactly one reprompt. Background handback uses the durable parent inbox, and forks take committed parent context through the spawning point. Worktree cleanup and cost attribution remain owned through settlement.

## Verification
Shared configuration/naming tests are groundwork, not proof of worktree isolation. Integration gates require real temporary Git repositories, concurrent processes, dirty/ahead preservation, session ownership, sandboxed setup, and child-runtime tests with deterministic providers. Native platform execution is required for subprocess and file-lock behavior. Keep M1.2 open until all product surfaces and behavioral contracts pass.


### Repository lock ownership
Use the standard-library file lock API, available at the workspace Rust 1.89 minimum, on the persistent `cyber-worktree.lock` file. Open read/write without truncating, try an exclusive lock without blocking and distinguish contention from I/O failure. A non-cloneable guard owns the file handle; drop or process termination releases it. Never unlink the file as cleanup, which could split cooperating processes across different lock-file identities. The lifecycle manager must resolve the shared repository Git directory before acquiring this primitive and hold it through a complete operation. Async contention polling must remain cancellable; active-session refusal is a separate durable ownership check. Native tests must prove independent processes contend, owner disposal releases, forced owner termination releases and separate repositories do not contend. These primitives alone do not close the concurrency requirement.


### Managed Git creation
A shared repository manager resolves root/common Git directories through an injected Git execution port. The application must supply sandboxed, cancellation-owned execution; the core manager has no default subprocess launcher. All mutating creation phases share the repository lock. Resolve the base to a verified commit ID, validate the complete branch name through Git and write a pending ownership record before creation. Never adopt an existing unowned target or branch. Successful creation records ready ownership; error/cancellation leaves pending evidence and preserves paths/branches for recovery rather than retrying checkout over possible user edits. Reuse checks the registered path, common repository directory and branch against ownership before returning, without resetting files. Session ownership, setup/includes, cleanup and recovery settlement remain subsequent required integration.

The cancellation regression observed lock contention immediately after dropping the creation future during parallel Git execution. Normal guard disposal now explicitly unlocks before closing the handle, rather than relying only on last-handle close; transient inherited descriptors must not extend normal ownership. Keep the cancellation assertion immediate and retain the independent-process forced-termination test.


### Git-for-Windows path arguments

Preserve canonical paths in records and filesystem checks; normalize only explicit Git path arguments into equivalent drive/UNC spelling and enable command-local `core.longpaths=true`. Do not change system/global Git settings. Refuse namespaces or filename components whose meaning changes when the verbatim prefix is removed, before writing ownership or creating a branch. Preserve Unicode through UTF-16 conversion. Native regression covers ordinary canonical targets, long paths and refusal of ambiguous names.

Native worktree execution at `1aeb710` passes seven repository cases but the long target fails in Git's automatic checkout with `$GIT_DIR too big`. Separate registration (`worktree add --no-checkout`) from index loading and checkout executed in the new directory with ambient Git overrides removed. Keep `checkout-index --all` non-forcing: a file created after registration must cause a pending creation error, preserving that file. Pending ownership spans all three stages; failure/cancellation tests retain completed checkout and user-file preservation controls. The existing long-path test remains required.

At `3405edc`, eight of nine native repository cases pass; long-path creation instead fails with Windows process-launch error 267. Windows launches now use a normalized ancestor shorter than 240 UTF-16 units and an explicit Git `-C` argument selecting the canonical requested directory's equivalent spelling. This applies to creation, verification and reuse; Git handles the directory switch after process creation. Runtime sandbox scope must follow the requested worktree rather than grant the launch ancestor. The native execution fixture checks short process directories, retains the long-path creation/reuse assertion and injects checkout collisions into the logical `-C` directory.

For long linked worktrees, use the verified short metadata directory for index/branch/common-directory operations and an explicit absolute `checkout-index --prefix` destination. Do not enter the long directory during Git setup. Verify the regular `.git` marker and metadata's `gitdir` backpointer canonically in both directions, retaining common-repository, branch and registration checks. Normal short-directory discovery is unchanged. Refuse unsupported long metadata directories rather than redirecting to a different repository or launching through an unverified alias. The original long-target creation/reuse and collision-preservation tests remain required.

### Untracked inclusion

Read `.worktreeinclude` through an opened source-directory capability and compile gitignore patterns with the existing `ignore` crate. Enumerate untracked files with NUL-delimited Git output, including gitignored files such as `.env`, and exclude paths tracked in the destination index. Validate relative paths before access. Copy regular files through confined source/destination directory handles, creating destination files exclusively; reject symlinks, special files and unsafe paths rather than copying outside either root. Preserve file permissions before copying content, record SHA-256 hashes of copied bytes for future cleanup accounting, and keep creation pending on any error. Reuse never repeats copying. Reverify repository ownership after inclusion before marking ready. Sandbox setup and runtime integration remain separate open tasks.

### Setup dispatch

The core setup dispatcher holds the repository lock, checks the supplied ownership against the persisted ready record and verifies repository/branch registration before invoking any setup command. Resolved settings must already have passed workspace trust. A required execution port receives the canonical worktree directory and an unbuffered event sink; there is no default host launcher. The runtime adapter owns sandbox permissions, credential filtering, process-tree settlement and delivery into the Session. Commands run sequentially and stop on the first nonzero or signal exit; lifecycle events bracket streamed byte chunks without requiring UTF-8. Exceptions, event delivery failure and cancellation leave files and ownership intact. Explicit setup invocation is not an automatic retry: durable runtime settlement must prevent blindly repeating side-effectful commands after interruption. Core tests with an injected execution port are foundation evidence, not acceptance of sandbox/process ownership or Session delivery.

### Built-in host setup adapter

`BuiltinHost::setup_worktree` requires the invocation Location to be the canonical managed path, resolves configuration through the existing trust-filtered host callback and checks the `worktree` permission before dispatch. Its private Git port performs ownership verification under the existing OS sandbox with ambient Git overrides removed, hooks/fsmonitor disabled and bounded output. Setup uses the same sandbox wrapper, credential filtering, proxy decisions, Session temp directory and process owner as shell tools; Windows selects installed native PowerShell without checkout-local resolution. Setup uses a strict preparation route that excludes the legacy shell wrapper’s ambient macOS user-temp grant; managed Session temp/output and explicit configured roots remain writable. Both streams are pumped within the owning future, not detached tasks. Output failure, cancellation and timeout terminate and reap the child. On Unix, setup observes leader exit with `waitid(WNOWAIT)` ([POSIX status consumption](https://pubs.opengroup.org/onlinepubs/9799919799/functions/V2_chap02.html)) before terminating its process group and reaping, so a still-owned leader prevents group identity reuse and pipe-holding descendants cannot prolong completion. Future disposal terminates an unreaped process group through the process guard. Windows uses the existing owned Job Object. Durable setup-attempt admission, automatic post-creation dispatch and actual Session event persistence/delivery remain required lifecycle integration; this adapter does not perform retries or declare Windows sandbox availability.

### Durable setup command journal

Register typed command-started and command-settled events in the existing runtime store registry. Each worktree has a dedicated aggregate derived from its persisted creation ID, canonical common directory, path, branch, base and name; its identity excludes the command recipe so config changes cannot hide existing intent. The recipe digest includes persisted managed ownership and all configured commands without storing source commands verbatim. Before dispatch, persist intent with expected-sequence concurrency through the single database writer. After process-tree settlement, persist exit/signal status or execution failure. Replay uses paginated events, rejects conflicting recipes and invalid intent/result ordering, reuses settled results and refuses any pending intent as outcome unknown. Successful earlier commands may be reused before admitting a later command that never started; failed or signalled predecessors prevent later admission. Idempotent settlement never appends a conflicting result. The host checks existing journal evidence even for an empty recipe and creates intent only through the setup execution port after core ownership verification under the repository lock. Cancellation returned by the process owner has a known settled failure; task disposal or process loss leaves pending intent. This prevents automatic side-effect redispatch but does not implement recovery resolution, automatic creation dispatch, Session event delivery or crash/orphan process cleanup.

New managed records receive a unique creation ID before Git mutation. Reuse preserves that ID. The journal includes it in aggregate identity so removal/recreation at the same path cannot reuse earlier setup results. Legacy records without a creation ID still deserialize for preservation, but journaled setup requires recovery rather than inventing a new identity that could hide previous intent.

### Session output delivery

A runtime-created sink requires an existing Session with matching canonical Location, ready worktree creation identity and a call ID. It publishes `session.worktree.setup` updates on the existing Location instance stream, matching the live-only delivery of other fragments; durable Session replay remains unchanged. Attempts may replay a journaled result and are labelled attempted rather than claiming a process started. Output updates identify command index and stdout/stderr and preserve arbitrary bytes in base64 chunks of at most 8192 source bytes. Command source is excluded. Finished updates carry exit/signal status; execution errors produce failure updates. The built-in host exposes a lifecycle wrapper that constructs this sink, runs the existing journaled setup adapter and holds a runtime lifecycle admission guard through cancellation and settlement. Shutdown cancels its private token and allows up to two seconds for acknowledged settlement before disposing the future, preserving pending intent as unknown when acknowledgement is missing. Real process tests must show output before completion, cancellation/shutdown stopping descendants and acknowledged cancellation on graceful shutdown. HTTP coverage must verify Location filtering and the event envelope. Automatic creation/enter dispatch, durable output artifacts and TUI rendering remain open; no arbitrary Location reassignment bypasses snapshot/rewind boundaries.

The HTTP stream regression exposed raw-versus-canonical Session Location comparison. A standalone directory-alias regression fails on committed main `1cff224` before the routing fix. Normalize the cached Session directory before comparing it to the already canonical request Location, preserving Location isolation and canonical envelope attribution. The regression stays explicit and the setup-output transport case continues to exclude another Location.

### Automatic creation to a fresh Session

The host creation entry point accepts a validated name, data/project identity and fresh Session options. It verifies the invocation against the persisted source Session Location and uses that Session's mode/rules for creation permission. Read-only sandbox policy, denied permission and cancellation refuse before target reservation. Discovery runs with no repository write grant; creation grants only the verified common Git directory and resolved target, plus managed temp/output and explicit configured roots. Git can provision metadata and tracked configuration files there; ordinary setup never inherits these provisioning grants. Hooks/fsmonitor and ambient Git overrides remain disabled, credentials filtered and processes cancellation-owned. After durable pending ownership, the core creates the target exclusively before Git mutation so Linux can bind that exact directory without granting its parent or siblings. Git failures preserve pending ownership and target.

Creation's runtime lifecycle guard covers owned Git execution. Fresh Session admission occurs after creation settlement, followed immediately by the existing attached, journaled setup wrapper. Shutdown in the intervening admission boundary fails explicitly and preserves the owned worktree; no nested lifecycle read acquisition is held across Session creation. Setup failure returns Session/ownership and its diagnostic rather than deleting work. Reuse preserves edits and uses durable setup results without repeating effects. This entry point is not yet exposed through CLI/API or subagents, and does not change the source Session Location; existing-Session enter/exit still requires snapshot-safe transitions.

### Public startup clients

`POST /api/v1/worktrees` accepts optional name/call ID and fresh Session options. Names/call IDs and existing-ID refusal are validated before host dispatch. The app service uses the established project identity and server data root; sandboxed creation still runs through the host's owned Git port. The explicit request authorizes only this creation/setup operation: a temporary policy evaluation treats ordinary approval requirements as approved, preserving denied rules, plan/read-only refusal and the selected persisted Session mode/rules. It creates no source Session. The response contains the actual Location, normal Session view, public worktree identity and a completed/failed/error setup status. Existing router idempotency wraps the whole request.

Both CLI startup paths subscribe to the all-Location live stream before creation and correlate setup updates using a fresh call ID; streamed bytes go to stderr so structured result stdout remains usable. Exec starts its prompt in the returned Session Location; TUI opens that existing new Session at the target. Named/generated flags cannot be combined with resume/fork or ephemeral exec. Management GET/DELETE, cleanup on exit, enter/exit transitions, durable setup artifacts and in-TUI rendering remain open. This is startup wiring, not full lifecycle acceptance.

Startup captures the resolved source worktree settings before provisioning and carries its already approved setup recipe into the automatic setup attempt. It does not approve the new checkout or reactivate its sensitive configuration. Target permission/sandbox configuration still resolves through the ordinary trust gate; explicit setup requested later uses that target's resolved settings. API tests cover global setup, approved source-project setup and inactive unapproved source setup, and assert no target trust approval is created.

The captured source recipe also retains its configured provider credential environment names, including disabled providers. Setup and its verification Git port add these exact names to the existing credential filter before wrapper-managed variables are added. This adds no credential lookup or target trust approval; explicit target env allow rules and user-selected full access retain their existing behavior. API project-trust tests configure HOME as a source credential and require it to be absent in setup, alongside the existing allow/full-access environment tests.

### Ownership listing foundation

The core repository listing holds the common-directory lifecycle lock and enumerates JSON ownership records in name order. Ready records are checked against repository, branch and Git registration; pending records are returned explicitly without assuming creation succeeded. Malformed, mismatched, oversized or symlinked records produce individual invalid-record diagnostics so one damaged record cannot hide the others. A missing ownership directory yields an empty list; a symlinked directory is refused. Inspection neither repairs ownership nor changes checkout contents. This foundation does not yet supply dirty/ahead/behind or Session activity, public management routes, removal or prune.

### Public management listing

Management listing matches both the canonical Location path and the Session's current managed creation binding before reporting ownership. It reads the binding from runtime state without cloning conversation history; replay preserves the durable identity. Older incarnations and historical unbound Sessions are excluded without editing their stored events. All pages, archived rows and children are still inspected. This is an informational ownership summary and cannot replace persistent activity admission for removal.

`GET /api/v1/worktrees` and `cyber worktree list` use a lifecycle-owned sandboxed Git port with no repository write grant. Ready status inspection reacquires the repository lock, verifies the persisted creation identity and Git registration, disables optional Git locks for porcelain status, and counts divergence against the original commit base. These are informational snapshots, not safe removal admission. HTTP enrichment paginates all stored Sessions, including children and archived rows, groups their canonical Locations and attaches matching rows. Pending and invalid records are represented separately without fabricated Git counts. Listing creates no Session. The SDK exposes `v1.worktree.list`; CLI JSON emits its data array. Removal, prune, active Session admission and exit cleanup remain open.

### Transactional removal foundation

Core removal holds the repository lock and requires an activity port whose guard must reject running Sessions and fence new Location use, including other server/embedded processes. It validates exact ready ownership and rejects dirty/ahead work unless forced; force never skips activity admission. Ignored files must be unchanged persisted inclusions to permit non-forced deletion. Both Git tree removal and conditional branch deletion use the required execution port; there is no host process default. Commands run from the common Git metadata directory so deleting the selected linked checkout does not invalidate the next command's launch directory.

A separate per-name removal journal records creation identity, admitted branch object ID, force choice and tree/branch intent and settlement phases. Files are synced and Unix parent directories are synced before progressing. Windows uses synced files plus rename but native power-loss durability is not proven. Recovery reconciles missing path/registration before branch settlement, rejects replacement paths, changed/checked-out branches and mismatched identities, and never redispatches a deletion with an unknown existing target. In particular a recreated branch with the same object ID cannot justify retrying an unacknowledged compare-and-delete. Completed tombstones preserve old-identity replay without touching a later creation. Creation/reuse/setup/status consult removal state; listing retains incomplete journals even after ownership unlink.

The activity port now has concrete cross-process leases used by Session creation and Drain admission. Core injected-port tests prove the manager protocol, while real-host tests cover running Drain refusal and checkout identity replacement. Other Location users still require fencing. Deleting the checkout root needs a removal-specific sandbox/filesystem boundary rather than reusing creation's exact-directory bind; that adapter, public DELETE/remove/prune, lifecycle events, automatic exit cleanup and process-crash/orphan resolution remain open. No public removal route is enabled by this foundation.

### Session checkout admission

Fresh Session creation records the exact managed checkout creation ID in its durable Created payload. Internally provisioned startup supplies the expected ID so a path replacement between provisioning and admission cannot be adopted. Forks retain the source binding; historical managed Sessions without a binding require recovery rather than silently adopting the current checkout. Ordinary directories, primary checkouts and submodules do not invoke Git solely for activity admission.

The tool-host Location port acquires a concrete cross-process checkout lease before each Drain's recovery, context, snapshot or model/tool access. The application host delegates admission to the built-in host, including Drains that use remote tools. Filesystem identification is informational; the core claim revalidates exact ready ownership and Git registration under the repository lock. The lease is held throughout the pass. Ordinary model/context errors settle when no dispatched or unknown calls remain; panic, future disposal and tools that miss their cancellation deadline retain unknown activity. Force never bypasses that evidence. This does not prove orphan-process cleanup after owner death.

Shell, manual rewind stage/clear, idle compaction and context repair now use the same Location admission and settlement helper as Drains. Idle operations retain runtime lifecycle admission until completion or bounded shutdown settlement. Built-in and application shell hosts receive an owned cancellation token; legacy hosts remain bounded by future disposal. Shell commands have two seconds to acknowledge shutdown. Compaction, rewind and context futures retain immediate shutdown disposal so their existing deadline is preserved. Disposed work retains unknown activity; ordinary acknowledged errors can settle, while panic and caller future disposal leave recovery evidence. Location claim futures are also bounded to two seconds after cancellation, including creation/fork admission. Recorded diff reads and conversation-only commit operations need no filesystem admission.

Session-backed setup now acquires the same checkout lease before taking its repository lock. One lifecycle owner bounds shutdown across both admission and setup, avoiding nested read-lock acquisition or successive grace periods. Acknowledged IO failures preserve their error kind and can settle activity after owned process cleanup. Owner disposal or missing acknowledgement releases OS locks but retains unknown activity, independently of the setup command journal. Real-process disposal tests must prove descendants stop while forced removal still refuses the unknown marker.

Idle client attachment, process-death recovery and unknown-activity resolution still need integration. Public removal and automatic cleanup remain disabled until the removal filesystem adapter and all relevant Location users are fenced.

Volumes without usable short aliases still need a supported initialization strategy before full Windows long-path coverage can be accepted.
