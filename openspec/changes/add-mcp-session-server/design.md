## Context

The server API is already the single contract every client uses: the TUI, `cyber exec`, the SDK and editors. It has local authentication (Unix-socket peer credentials, HTTP Basic with the local password), idempotency keys, tagged errors, durable prompt admission with receipts, durable event replay and a Messaging API. External agents want the same control through MCP, the protocol they already speak. The user chose the trusted local client model: an MCP client is one more local client of that API, not a new kind of principal.

An earlier draft treated MCP clients as untrusted principals, with grants, tokens, an MCP sandbox, approval relay and human-only classes. It reached 52 requirements and touched 20 capabilities. Under the chosen model that machinery protects nothing: any process that can reach the endpoint with the local password or as the same OS user can already call the server API directly.

## Decisions

- **Thin mapping.** Each tool maps to one or two existing routes and keeps their semantics: `POST /api/v1/sessions`, `GET /api/v1/sessions[/:id[/messages]]`, `POST .../prompt`, `POST .../interrupt`, `GET|POST /api/v1/messaging/...`. Idempotency keys, tagged errors, durable events and inbound messaging controls are reused. The only new semantics are the wait/receipt layer, the Mode ceiling and the safety bounds.
- **Two transports, one server.** `cyber mcp serve` (stdio) is a bridge to the registered shared server, never an embedded one, so MCP-driven Sessions are visible in the TUI, where a human can answer their approvals. Streamable HTTP is served at `/api/v1/mcp/serve` on the existing listener (`mcp` route group), so `server-api` and `cli-commands` need no change. Streams are not resumable: a lost call is recovered through the receipt, `cyber_prompt_wait` and the idempotency key.
- **One protocol revision.** `2025-06-18` is supported by every current MCP client and SDK, has `outputSchema`/`structuredContent`, Streamable HTTP, progress and cancellation, and has no tasks utility to exclude. A client that requests a newer revision is answered with `2025-06-18` by normal negotiation. Supporting a second revision (and later the stateless one) is additive.
- **Waiting.** `cyber_prompt` waits by default up to `wait_seconds` (default 50, below the common 60 s client request timeout, so the receipt comes back before the client gives up; clients with longer timeouts may pass up to `max_wait_seconds`, 600). It returns early when its run raises a permission or question request (`waiting_for_approval`), so an agent never waits silently on a human. Hitting the timeout returns the receipt, not an error. `wait_seconds` is clamped to `max_wait_seconds` at run time, so cached schemas never go stale. Cancellation never rolls back a write: a `cyber_prompt` cancelled before admission still creates and admits. Replay applies per underlying write: a write with a stored idempotency key replays before the quota, concurrency and ceiling checks and is never re-counted, so recovery always works; `cyber_prompt` always keys its writes `...:session` and `...:prompt` and looks up `:prompt` first. `cyber_prompt_wait` re-attaches from durable events after restarts. Requests already pending when a wait began do not end it, so polling never busy-loops.
- **Cancellation stops waiting only.** `notifications/cancelled`, closed streams and bridge EOF never interrupt; only `cyber_interrupt` does. This keeps one simple rule and avoids an agent killing a human's Turn by cancelling a wait.
- **Approvals are not relayed.** MCP connections are not interactive clients, so the existing `permissions-modes` "Non-interactive behavior" applies to permission requests unless a TUI, web or SDK client is attached. Sessions created through MCP carry the `exec-mode` non-interactive Session rules (no `question`, `plan_enter`, `plan_exit`), so they never block on a human answer. Results report `waiting_for_approval` and `pending`. Relay through elicitation is a P2 requirement.
- **Mode ceiling.** The server API lets any client choose a Mode, so MCP calls are bounded: an explicit `mode` or `agent` above `mcp_serve.max_mode` (default: the user's global `mode`, never `bypass`) is refused, an implicit Mode (default agent or Location default) is clamped to it, `dont-ask` ranks below `default`, and no tool changes Mode afterwards. The ceiling applies at creation only: an MCP client drives an existing Session as any SDK client can, and prompt text is never resolved as a slash command, so `/mode` cannot run from `cyber_prompt`. The ceiling is global-only, so a cloned repository cannot raise it.
- **Recursion guard.** Each admitted input carries a depth, stored with it (MCP request depth, the sender run's depth for a native `send_message`, 0 for user input), and a Session's `mcp_depth` is the depth of the input that started its current run, raised by deeper inputs promoted into that run. Depth is run-scoped, not Session-scoped, so a long-lived coordinator that was once messaged is not disabled for good. Processes get `CYBER_MCP_DEPTH`, and Cyber's MCP client adds a `_meta` caller marker toward `cyber-code` servers (it wins over `X-Cyber-MCP-Caller`). Because messages carry depth too, prompt loops between existing Sessions stop even when one leg uses `send_message`. Mutating calls at depth ≥ `max_depth` (default 2: one level of Cyber driving Cyber) and self-targeting calls are refused. Fan-out is bounded by `max_depth`, messaging rate limits and `max_running_sessions` (running Sessions created through MCP serve or whose current run was started by MCP input; only `cyber_prompt` is refused by it); `sessions_per_connection` is only a per-connection limit.
- **Attribution.** MCP prompts use the public user-admission path (`source: "user"`, so `UserPromptSubmit` hooks run); no new origin kind. A message sent through MCP by a known caller Session is sent as that Session (origin `session`), exactly as its own `send_message`; otherwise it uses the Messaging API origin `client`. Either way the receiver's inbound rules apply unchanged. MCP serve keeps `mcp_client` and input depths in its own records keyed by `session_id` and `message_id`; the runtime stores the sender's depth with a native `send_message`, so `session-runtime` requirements are unchanged. Usage of runs started by MCP input is tagged `origin: mcp` with `mcp_client`. The label comes from `--client` or `clientInfo.name` and is used for attribution only, never for authorization.

| `cyber_message_history` | `GET .../messaging` | `session_id`, `cursor?`, `limit?` 1..100 = 50, `max_bytes?` 1024..196608 = 65536 | `{ messages[], next_cursor?, truncated }` |

Shared shapes:
- `SessionSummary` = `{ session_id, title, directory, parent_id?, agent, model, mode, state: idle|running|waiting_for_approval, mcp_client?, mcp_depth, created_at, updated_at }`
- `PromptResult` = `{ session_id, message_id, status: queued|running|waiting_for_approval|completed|failed|interrupted|budget_exceeded|refused, done, stop_reason?, final_text? ≤ 64 KiB, truncated?, usage?, turns?, pending?, error?, replayed?, admitted_at, finished_at? }`
- `PendingRequest` = `{ request_id, kind: permission|question, session_id, summary ≤ 512, created_at }`
- `Usage` = `{ input_tokens, output_tokens, reasoning_tokens, cache_read_tokens, cache_write_tokens, cost_usd|null }`

Successes return `structuredContent` and `content[0]` as its serialized JSON, with no separate summary block. Errors are returned with `isError: true` as JSON text in `content[0]`, without `structuredContent`. Error reasons added by this capability, all as `server-api` tags: `InvalidRequestError` (`schema`, `too_large`, `exclusive_fields`, `session_settings_on_existing`, `not_a_directory`, `mcp_session_required`), `NotFoundError` (`mcp_session`), `ForbiddenError` (`loopback_only`, `host_not_allowed`, `mode_ceiling`, `session_quota`, `depth_exceeded`, `self_target`), `RateLimitedError` (`concurrency`), `ConflictError` (`idempotency_mismatch`).

## Trust model and threat notes

- **Who can connect.** Only a process that holds the local password (mode 0600 file) or runs as the server's OS user on the Unix socket. That process can already call every server API route, read the database and start `cyber` itself. Grants, tokens or an MCP sandbox would not stop it, so the trusted-client model loses no real protection and avoids a second authorization system.
- **Network exposure.** The endpoint accepts only the Unix socket and loopback TCP peers with local credentials, even when `cyber serve --hostname` binds a LAN address; Bearer, Relay and `/api/v1/ws` requests are refused. Remote access waits for the P3 OAuth resource server.
- **Browsers and DNS rebinding.** The `server-api` Origin policy still applies, and the endpoint also requires a loopback `Host`, so a web page cannot use a rebinding DNS name to reach it.
- **Prompt injection between agents.** Session output is marked untrusted (`_meta["dev.cyber-code/untrusted"]`), messages keep the messaging untrusted block, and prompts are literal text that cannot run commands, approve requests or change the Mode. The calling agent remains responsible for what it sends, as with any SDK script.
- **Unattended escalation.** Approvals never go to the MCP client; Sessions without a human resolve requests by their Mode's non-interactive rules. The Mode ceiling bounds Sessions created through MCP; existing Sessions keep their own Mode and can be driven as by any SDK client.
- **Runaway fan-out and cost.** The depth guard, per-connection Session quota, running-Session cap and wait cap bound recursion. No budget applies unless the user configures `budgets.session` or `budgets.daily`; MCP-driven usage is bounded by depth and the running cap. The markers are accident guards: a same-user process that strips them could call the API directly anyway.

## Deferred

- P2: per-client grants and roots (`cyber mcp clients`), approval relay through elicitation (opt-in, human-only classes), team task list and claims over MCP (`agent-teams`), workflow and goal tools.
- P3: non-loopback and Relay access as an OAuth 2.1 protected resource with Cyber Account tokens.
- Not planned for P1: MCP tasks, resources and subscriptions, a second protocol revision, resumable streams, an `interrupt_on_cancel` option, `format` (structured output) on `cyber_prompt` (the prompt route does not take it), `hold` delivery and inbox decisions, idle-watch notifications.
