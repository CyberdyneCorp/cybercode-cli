# Feature reference

Implemented behavior and remaining scope, reviewed on **2026-10-11**. Start with the [README](../README.md); use the [P1 status](implementation/p1-status.md) and [acceptance audit](implementation/p1-acceptance-audit.md) for detailed evidence.


“Available” describes implemented local-core behavior. “Partial P1” means working pieces exist and the full contract still needs implementation or acceptance.

Tools create, list, read and page Sessions, send literal prompts through the user path (`UserPromptSubmit` hooks run) with a wait or a receipt, re-attach with `cyber_prompt_wait` (also after a restart) and interrupt. Waits answer over SSE with keep-alives and progress; cancellation ends only the wait. Idempotency keys replay one effect, a global-only Mode ceiling bounds new Sessions, and `sessions_per_connection`, `max_waits` and `max_running_sessions` refuse before any write. A recursion guard refuses calls nested `max_depth` deep through Sessions and a Session driving itself or its ancestors. Approvals are never relayed | Partial P1; messaging tools and their depth, `origin: mcp` usage, unattended approval rules and native acceptance remain |

Remaining P1 scope includes hooks/plugins/MCP (M1.3), memory/code intelligence/browser verification (M1.4), migration (M1.5), the local web client and the other P1-tagged APIs. Workflows, goals, loops, remote control, cloud runners and editor integration (ACP, VS Code) belong to later phases; the P2 Workflow runtime (M2.1) is implemented without its TUI monitor: `cyber workflows list/run/runs/show/pause/resume/stop/logs` (with `run --wait` exit codes 0/1/4/130), the model's `workflow` tool behind the `workflow.run` permission, the sandboxed engine with real child-Session agents, default worktree isolation for concurrent writers, pause/stop/resume with durable replay across server restarts, checkpoints, run budgets, per-run usage, run results with one queued summary to the starting Session, `WorkflowRunStart`/`WorkflowRunEnd` hooks, live run events on the event stream, the `v1.workflow.*` OpenAPI operations and the SDK's `client.workflows.run()` handle; the runtime was accepted end to end with the real `cyber` binary against a scripted local provider (fan-out under the concurrency cap, background HTTP runs, determinism guards, resume after the server is killed, budget exit 4, stop, `workflow.run` deny rules and Mode ceilings). `ask()`, direct read-only tools, prompt-cache warm-up, `exec --workflow`, Job (`/tasks`) integration, saved-Workflow listing over HTTP, reserved budgets and the TUI monitor remain (see [P2 evidence](implementation/p2-status.md)). `CYBER.md` instruction files are not loaded yet; project instructions come from `AGENTS.md`, `CLAUDE.md` and `CONTEXT.md`. The [capability map](local-core-guide.md#specification-capability-map) covers the full planned product; [OpenSpec](../openspec/specs) defines the contracts by phase.


Read-only migration previews are available with `cyber import <claude|codex|opencode|auto> --dry-run [--scope project|global] [--format json]`. They propose supported permission/model/provider and basic Codex approval/sandbox fields without creating configuration, logs or databases. Existing native keys win; auto fills missing keys in OpenCode, Codex, Claude order. Literal credentials become required environment references rather than copied values. Unsupported sources are listed explicitly. Native global/ancestor/`.cyber` file layers use runtime merge rules, without evaluating profiles or substitutions. Supported leaves and environment requirements carry source paths/pointers. Output is a redacted normalized JSON diff; original-byte/comment-preserving diffs, complete source adapters/reports and confirmed writes remain open. JSON reports keep `complete: false`.
