Remaining P1 scope includes hooks/plugins/MCP (M1.3), memory/code intelligence/browser verification (M1.4), migration (M1.5), the local web client and the other P1-tagged APIs. Workflows, goals, loops, remote control, cloud runners and editor integration (ACP, VS Code) belong to later phases; the P2 Workflow runtime (M2.1) is implemented, with the `/workflows` TUI monitor: `cyber workflows list/run/runs/show/pause/resume/stop/logs` (with `run --wait` exit codes 0/1/4/130), the model's `workflow` tool behind the `workflow.run` permission, the sandboxed engine with real child-Session agents, default worktree isolation for concurrent writers, pause/stop/resume with durable replay across server restarts, checkpoints, run budgets, per-run usage, run results with one queued summary to the starting Session (up to 8 summaries that end together share one Turn), several runs at once (`add-parallel-workflow-runs`: at most `workflows.max_running_runs` running with the rest in a run queue dispatched oldest first, fair least-recently-granted sharing of the `workflows.max_concurrent` agent slots with a per-run `max_concurrent` share and `workflows.max_concurrent_per_run`, independent per-run pause/stop/resume, crash recovery that pauses interrupted runs and keeps queued ones queued, `cyber workflows resume --interrupted`, `workflows.resume_after_restart`, run summaries with live counts, filters and `workflow.run.progress`, `cyber workflows runs --watch`, the SDK's `client.workflows.list()`/`get()`), `WorkflowRunStart`/`WorkflowRunEnd` hooks, live run events on the event stream, the `v1.workflow.*` OpenAPI operations and the SDK's `client.workflows.run()` handle; the runtime was accepted end to end with the real `cyber` binary against a scripted local provider (fan-out under the concurrency cap, background HTTP runs, determinism guards, resume after the server is killed, budget exit 4, stop, `workflow.run` deny rules and Mode ceilings), and parallel runs were accepted the same way (three runs at once with fair grants, the queue, independent pause/stop/resume, `kill -9` recovery, `runs --watch`, the TUI monitor in a pty); that acceptance is also automated (`crates/cyber-cli/tests/parallel_workflows.rs` against the real binary and server, `crates/cyber-tui/src/screens_parallel.rs` through `TestBackend`). `ask()`, direct read-only tools, prompt-cache warm-up, `exec --workflow`, Job (`/tasks`) integration, saved-Workflow listing over HTTP and reserved budgets remain (see [P2 evidence](implementation/p2-status.md)). `CYBER.md`, Cyber Code's own instruction file, loads with `AGENTS.md`, `CLAUDE.md` and `CONTEXT.md` (change `add-cyber-md`). The [capability map](local-core-guide.md#specification-capability-map) covers the full planned product; [OpenSpec](../openspec/specs) defines the contracts by phase.


Read-only migration previews are available with `cyber import <claude|codex|opencode|auto> --dry-run [--scope project|global] [--format json]`. They propose supported permission/model/provider and basic Codex approval/sandbox fields without creating configuration, logs or databases. Existing native keys win; auto fills missing keys in OpenCode, Codex, Claude order. Literal credentials become required environment references rather than copied values. Unsupported sources are listed explicitly. Native global/ancestor/`.cyber` file layers use runtime merge rules, without evaluating profiles or substitutions. Supported leaves and environment requirements carry source paths/pointers. Output is a redacted normalized JSON diff; original-byte/comment-preserving diffs, complete source adapters/reports and confirmed writes remain open. JSON reports keep `complete: false`.
